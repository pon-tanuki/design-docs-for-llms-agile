# ドキュメントフォーマットガイドライン

このドキュメントは、本リポジトリ内のすべてのドキュメントが従うべき共通フォーマットを定義する。
生成AIがドキュメントを正確に解釈し、一貫性のあるコードを生成できるようにするためのルール集である。

## 1. ファイル命名規則

### 基本ルール

- ケバブケース（kebab-case）を使用する
- 英小文字とハイフンのみを使用する
- 日本語ファイル名は使用しない

### 命名パターン

| 種類 | パターン | 例 |
|------|----------|-----|
| テンプレートファイル | `_template.md` | `_template.md` |
| 機能仕様 | `feature-<機能名>.md` | `feature-login.md` |
| API仕様 | `api-<リソース名>.md` | `api-users.md` |
| 設計ドキュメント | `<カテゴリ>-design.md` | `api-design.md` |

## 2. ドキュメントヘッダー（Front Matter）

すべてのMarkdownドキュメントは以下のFront Matterで始める。

```yaml
---
id: <一意のID>
title: <タイトル>
status: draft | review | approved | deprecated
created: YYYY-MM-DD
updated: YYYY-MM-DD
author: <作成者>
related: [<関連ドキュメントID>]
---
```

### フィールド説明

| フィールド | 必須 | 説明 |
|-----------|------|------|
| id | はい | ドキュメントを一意に識別するID（例: `US-001`, `API-002`） |
| title | はい | ドキュメントのタイトル |
| status | はい | `draft`（下書き）, `review`（レビュー中）, `approved`（承認済み）, `deprecated`（廃止） |
| created | はい | 作成日（YYYY-MM-DD形式） |
| updated | はい | 最終更新日（YYYY-MM-DD形式） |
| author | はい | 作成者名 |
| related | いいえ | 関連するドキュメントIDの配列 |

### IDの命名規則

| 種類 | プレフィックス | 例 |
|------|---------------|-----|
| ユーザーストーリー | US- | `US-001` |
| 機能仕様 | FEAT- | `FEAT-LOGIN-001` |
| API仕様 | API- | `API-001` |
| データモデル | DB- | `DB-001` |
| 設計ドキュメント | DOC- | `DOC-ARCH-001` |

## 3. セクション構造

### 見出しルール

- H1（`#`）はドキュメントタイトルのみ（1つだけ）
- H2（`##`）は主要セクション
- H3（`###`）はサブセクション
- H4（`####`）以下は控えめに使用

### 良い例

```markdown
# ログイン機能仕様

## 概要

## 要件

### 機能要件

### 非機能要件

## 完了条件
```

### 悪い例

```markdown
# ログイン機能仕様

# 概要（H1が複数ある）

#### 詳細（H2, H3を飛ばしている）
```

## 4. リスト記法

- リストは `-`（ハイフン）を使用する
- `*`（アスタリスク）は使用しない
- 番号付きリストは `1.` で統一（自動採番を活用）

### 良い例

```markdown
- 項目1
- 項目2
  - サブ項目2-1
  - サブ項目2-2
```

### 悪い例

```markdown
* 項目1
* 項目2
```

## 5. AIフレンドリーな記述ルール

### 曖昧な表現を避ける

| 避けるべき表現 | 推奨される表現 |
|---------------|---------------|
| 適宜 | 〜の場合は〜する |
| 必要に応じて | 条件Xを満たす場合は |
| など | 具体的に列挙する |
| 適切に | 具体的な基準を示す |

### 構造化データを活用する

AIは構造化されたデータを解釈しやすい。可能な限りYAMLやJSONを使用する。

```yaml
inputs:
  email: string（必須、RFC準拠）
  password: string（必須、8文字以上）

outputs:
  token: string（JWT形式）
  expires_at: datetime（ISO 8601形式）
```

### 正例・負例を明示する

```markdown
## バリデーション

### 正例（有効な入力）

- email: `user@example.com`
- password: `SecurePass123`

### 負例（無効な入力）

- email: `invalid-email`（@がない）
- password: `short`（8文字未満）
```

### 略語は初出時に正式名称を併記

```markdown
JWT（JSON Web Token）を使用して認証を行う。
以降、JWTと表記する。
```

## 6. リンク規則

### 内部リンク（相対パス）

```markdown
詳細は [ログイン機能仕様](./feature-specs/feature-login.md) を参照。
```

### 外部リンク

```markdown
[OpenAPI Specification](https://swagger.io/specification/)
```

### アンカーリンク

```markdown
[バリデーション](#バリデーション)
```

## 7. コードブロック

### 言語を必ず指定する

```markdown
```yaml
key: value
```

```json
{ "key": "value" }
```

```sql
SELECT * FROM users;
```
```

### インラインコード

- 変数名、ファイル名、コマンドはバッククォートで囲む
- 例: `user_id`, `config.yaml`, `npm install`

## 8. プレースホルダー表記

### 山括弧形式

置換が必要な箇所は `<山括弧>` で囲む。

```markdown
# <プロジェクト名>

## 概要

<プロジェクトの概要を記述>
```

### オプション項目

オプション項目には `<!-- optional -->` コメントを付ける。

```markdown
## 関連ドキュメント <!-- optional -->

- [関連仕様1](./spec1.md)
```

## 9. テーブル記法

### 基本形式

```markdown
| 列1 | 列2 | 列3 |
|-----|-----|-----|
| 値1 | 値2 | 値3 |
```

### 配置指定

```markdown
| 左寄せ | 中央 | 右寄せ |
|:-------|:----:|-------:|
| 左     | 中   | 右     |
```

## 10. 注意事項・警告の記法

重要な注意事項は以下の形式で記述する。

```markdown
> **注意**: この操作は取り消せません。

> **警告**: 本番環境では使用しないでください。

> **ヒント**: 開発環境では `DEBUG=true` を設定すると詳細ログが出力されます。
```

## チェックリスト

ドキュメント作成時に以下を確認する。

- [ ] Front Matterが正しく記述されているか
- [ ] H1は1つのみか
- [ ] リストは `-` を使用しているか
- [ ] コードブロックに言語が指定されているか
- [ ] 曖昧な表現がないか
- [ ] プレースホルダーは `<山括弧>` 形式か
- [ ] 相対パスでリンクしているか
